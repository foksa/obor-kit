# State model

What `obor serve` records, in what order, and what a restart does with it. Packages: `docs/module-map.md`; the gate
split: `internal/checks/scratch.go` (`Scratch`: submit, gate, publish) and `app.Candidate` (`internal/app/effects.go`).

There is one `obor serve` per project (T-522): started in the project, it serves that project only. At its start it takes the flock
`<root>/.obor/state/serve.flock` (it names the serve's pid; the log's one writer), refused with `FAIL obor serve
already runs for <root> (pid …)` while another serve holds it, and listens on `<root>/.obor/state/serve.sock` (a path
over the unix socket limit, 104 bytes on macOS, fails the start naming it). Every CLI dials the socket of the project
it runs in (a lane worktree's is its main checkout's); `obor send` dials the target's. Both go when serve ends.

## The log

- One append-only table per project: `events` in the project's SQLite database `.obor/state/obor.db` (T-435,
  `internal/store`). One row per record, inserted in its own transaction (`synchronous=FULL`: on disk before the
  effect starts); a failed insert rolls back, so no partial record exists. Replay reads the rows in `seq` order.
- A dispatch that waits is `obor dispatch … --after`, or one with no free lane of its level (row 2a).
- The lane state is the same database's `lanes` table (T-439): `lane, task, branch, agent, base, head, dispatched_at,
  finished`, a projection of the log, not a log. serve is its one writer: after the load's replay and after every
  record that changes a row it rewrites the table from its fold (`internal/app/lanerows.go`). A successful
  `lane.prepare` puts its task on the lane (and off any other lane), a `dropped` fact takes it off, `finished` is when
  the attempt's `task_done` was recorded (0 while the task awaits it). After a merge the row stays until the lane's
  next dispatch. Readers open it read-only (`store.ReadLaneAt` / `ReadLanesAt`), so they work with serve down: the
  guard's protected unlocks (a read error unlocks nothing), whoami, SessionStart, UserPromptSubmit, the worker Stop hook,
  `obor status` (through `checks.LaneTable`), the agent lookups of `project.LaneAgent` (launch, setup). `obor mcp`'s
  `task_done` names only the caller's lane
  (`OBOR_LANE`): serve resolves it to the row's task.
- The tasks' specs are the same database's `specs` table (T-440): `task, text, rev, set_by, set_at`. serve is its
  one writer: `obor spec set T-xx <path>` (any file, read once) is a `spec_set` socket request, accepted from the lead
  or the owner (no role; `set_by` "owner") and refused for every other role (a worker cannot unlock files, T-238); a set with another text is the next rev, the same text changes
  nothing. Readers: dispatch (a stored spec is required, row 2), the work job's text
  (it carries the current rev; a fix job carries it when the rev changed since the worker's last fetch: the
  `delivered` fact records the rev a job carried), the guard's protected unlocks, whoami and SessionStart (read-only: a
  change applies at the next hook call), the commit subject (`titleOf`), the flakes rule, `obor spec
  show` / `list` (read-only, serve up or down). The gate puts the current rev into every candidate's merge message, no file
  in the tree (T-521): `Merge T-xx: <title>`, a blank line, `Spec rev N:`, a blank line, the text (lane, moved: the
  merge it commits; resolved: the integrator's merge amended after its subject, the merge's committer date, so a repeat
  makes the same commit). The gate's result records the rev (`gate.spec_rev`); the review job names that rev and carries its text
  (changed since: the current text, and the merge message as the gated rev's), so an accept binds to what was reviewed, and `git log` has each spec in its merge. A dropped task's spec stays in the store only. The lead drafts specs in
  `.obor/drafts/` (gitignored), never in the tasks dir (an untracked file there holds the publish).
- `obor serve dump [<root>]` prints the table as JSONL (read-only, serve may be down). `obor nightly` backs the database up to
  `.obor/state/backup/obor-<YYYY-MM-DD>.db` (through the running serve, else directly), keeping the newest 7.
- One writer: the serve holding the project's `serve.flock`. A failed append (disk full, read-only) is kept in memory
  as the project's `log_error` until an append succeeds: `obor status` prints it (T-424). That reason is not a record: while the log fails, no
  step, needs-you included, can be recorded.
- A record: `{"seq":41,"ts":"…","task":"T-12","attempt":2,"step":"publish","kind":"intent|result|fact","data":{…}}`.
  - **fact**: a decision with no outside effect (a verdict, a transition, a watchdog firing).
  - **intent** before every outside effect, **result** after it, same key.
- Idempotency key (task, attempt, step). `attempt` goes up on each dispatch and each sendback. A step that repeats
  inside one attempt carries a counter (`gate.2`, `prompt.retry`). A second intent for a key that has a result is
  never written; the stored result is used.
- MCP calls (job_next's fetch, task_done, accept, sendback, reject, resolved, hold) carry a call id. The verdict record holds
  it; a repeated call id gets the stored reply and changes nothing.
- **Replay** = fold the records in `seq` order into state, then **reconcile** every intent without a result: the
  effect may or may not have happened. The intent's crash class (below) says how it is settled. Reconcile writes the
  missing result (or a new intent), so a second crash during reconcile replays the same way. A crash between intent
  and effect is the same case as one between effect and result.
- **An ended task's intents are not pending** (T-400; `settleEnded` in `internal/app/loop.go`): an intent of a task
  that is merged or dropped, of any attempt, is settled as nothing, result `"not run: <task> <state>"`, never run
  again (folded as no outcome). The loop runs no step of a dropped task and only the after-merge steps of a merged
  one, so nothing else would close them: an earlier attempt's (a redispatch, a later submission), or the ended
  attempt's own (a prompt refused before typing, a start that failed). Replay settles them first, and the live path
  as soon as the merged or dropped fact is folded. Kept as before: a merged attempt's after-merge steps, a
  verdict's intent (its call id's reply), one whose result is unwritten in this process; and, merged or dropped
  alike, the notification of every needs-you still in force, the merge loop's or a watchdog's (T-401: the same facts
  notify shows, `needsYou`); one whose fact has cleared is settled. An intent of an open task replays as below.
- Bindings: the integrator's **accept** is bound to the patch hash (sha256 of `git diff <Candidate.Target>
  <Candidate.SHA>`). The **gate** result is bound to (candidate tree, target HEAD). When the target moves and the new
  candidate's patch hash is byte-identical, the gate re-runs and the accept stands.
- A **job** is one prompt to an agent, id `<task>/<attempt>/<step>`. It is delivered when the agent's first tool call
  quotes the id (timers below). herdr status alone never proves delivery (`agent.prompt` to a working Claude queues,
  it is not refused).

## Crash classes

Every transition below names one class. A prompt (a job's wake, a line) has none: its intent (class `prompt` in the
log; replay reads no intent's class) is sent again by the step that reaches it, whatever a crash left ("Prompts"
below, T-524).

- **F — pure fact.** One record, no outside effect. Replay: it is there or not; if not, nothing happened and the
  caller retries (an MCP call id returns the stored reply). A notify after a fact is not recorded; replay notifies
  again. A client whose reply is lost (a reset, a close, or a serve that crashed before answering) retries the same
  request and call id with backoff for about 30 s (`ask`): the restarted serve replays and answers from its store.
  After the budget the client gets the last refusal, and that means the call may have landed: its reply is still
  stored for that id, so the same id is the only way to learn it.
- **S — start/stop, checked via the snapshot.** Replay reads `session.snapshot`: agent in the pane (start) or none
  (stop) → the effect happened, write the result; else do it again (Start no-ops on a pane with an agent).
- **G — git effect, a function of durable inputs.** Each step's effect reads only shas in the app's records and the
  pins under `refs/obor/` (the `Scratch` adapter, serve's own worktree), never
  the worktree's state: every gate starts with a reset, publish checks ancestry first (the target contains
  `Candidate.SHA` → already; the target moved → moved, row 32). A repeat from any cut converges; after_merge must be
  idempotent. Its git runs under the step's ctx, in its own process group: serve's stop kills
  a blocked git and returns (the attempt is not counted).
  **Git lock contention** (T-382; every `Scratch` git call, `gitLocked` in `internal/checks/gitlock.go`): a call that
  cannot take a lock (`index.lock`, a ref's `.lock`: "Unable to create '….lock': File exists") is transient, not a
  counted failure: it waits for the lock to go and runs again. obor's own lane reads (`git status`, each tick) take
  the lane's `index.lock` for a moment, so submit's `git add` meets it now and then. A lock older than 60 s with no
  git process running in the repository's worktrees (`ps` and each git's cwd; an unreadable one counts as running)
  is stale, a killed git's (a git orphaned by a `kill -9` of serve still runs: its lock is waited for): it is removed
  once per call and logged, then the
  call runs again. Past 60 s of waiting in one call (a hung holder, a stale lock that is back) the call's error is the
  step's, counted.

A crash can come **before an effect** (its intent written, the effect never ran) or **after it** (the effect done,
its result lost); replay cannot tell the two apart, so every effect is safe to run again at either point. A pending
intent's effect is run again under the same key: its intent line is reused, never written twice.

**The failure rule** (T-340; every merge-loop effect, `App.do` in `internal/app/loop.go`): an effect returns a result
only for an outcome final for its step (below). Anything else is an error: no result, the step stays pending and is
tried again on the next pass. Each counted failure is a fact `failed{<step>: <why>}` (data `step`: the key), so a
restart keeps the count; the 3rd is `needs-you{<step> failed: <why>}` (cause `<step> failed`). A merge-loop needs-you carries `merge: true` and its `cause`; a watchdog's facts do not. While a merge-loop needs-you is in force no pending step of the task is attempted. The count resets only on `unblocked`;
`obor resume`'s default for `<step> failed` is `retry` (back to the state the needs-you left: the pending step runs
again). An attempt cut off by ctx (obor serve stops) or ending while herdr is disconnected is not counted. A git
step's adapter returns `(outcome, error)`: an outcome is final, a Go error is the retry (no error types, no text
classification). A later after-merge step never runs while an earlier one is pending (no lane reuse after a failed
stop). An effect that ran and whose result's write failed is not run again in that process (T-371): the
next pass writes the result it had; after a restart its crash class settles it.

## Prompts (T-371, T-524): the wake contract

Every prompt (`work[.N]`, `retry.work[.N]`, `fix`, `review[.N]`, `resolve[.N]`, `retry.<job>`, `nudge.<job>`, an owner's
reprompt as the next job) is a job's wake, `[obor job <id>] call the obor job_next tool` (a nudge's reminder line
before it): one constant line, harmless typed twice, lost or eaten by a dialog. The helper `App.send`
(`internal/app/prompt.go`) sends it under its key: posted to the agent's session when its pane's kind has an inbox
(Claude, `agents.Caps.Inbox`) and its session an inbox record (`Loop.Inbox.Post`, T-499), else typed into the pane
`whereIs` resolves right before the send (row 48; never herdr's agent name), its input line cleared first
(`Loop.Typer.Type`, `herdr.Panes.Type`: `ctrl+u`, then `agent.prompt`, no key after it: a bare Enter could choose a
dialog option, T-417). Not identified (two panes claim the agent, none proves it, not connected): nothing sent or
recorded, the key stays pending. Refused before a byte went out (herdr's refusal, no connection, a refused dial, the
clear failing): a counted failure (the failure rule), sent again under its key. A byte went out, then an error:
result `sent: <error>`. The proof of delivery is the agent's `job_next` (fact `delivered`), never the send; the
delivery timers (rows 7–8) send the wake again until then, then tell the owner. A pending prompt intent (a crash) is sent again by the step that reaches it; nothing settles it
on replay. Lines (row 47) take the same transport (`transmit`), without the clear.

A worker's `fix` job has the work job's delivery timers (rows 6–8: `retry.fix`, then `needs-you{job not delivered}`;
`obor resume` retries it as `fix.2`, T-419): delivered by its `job_next`, it waits for the worker's `task_done`.
Residual: a clear is `ctrl+u` (the input line); a multi-line draft is not proven cleared by it.

Every agent fetches its jobs (T-437): there is no typed job text and no status rule of delivery.

## States

Task, exactly the states the code has (`internal/app/loop.go`): **submitted** (submit the lane's commit, then gate it)
· **green** (gate green: a review job, or an accept already bound to the patch) · **awaiting-accept** (the review job
is out) · **red** (gate red: a sendback, or the owner after K) · **conflict** (the merge conflicts in the scratch: a
resolve job) · **resolving** (the resolve job is out) · **resolved** (gate the merge the integrator committed in the
scratch) · **fail** (the owner decides why) · **accepted** (publish it) · **moved** (gate the candidate again on the
new target) · **published** (the target holds the candidate) · **merged** (terminal, then the after-merge steps) ·
**rejected** (terminal; the owner is told) · **dropped** (terminal; the lead abandoned it) · **waiting** (a dispatch
that waits for the tasks it names to merge, row 2a) · **dispatched** (a dispatch's steps: `lane.prepare`,
`agent.start`, the work job) · **working** (the work job delivered, or
sent back: the fix job; then its `task_done`) · **needs-you** (the owner decides; the state it left is kept).
The code mirrors this as one table, `states` in `internal/app/states.go` (T-436): a row per state with its next
step, step name, verdicts, sendback, resume rule and scratch, each naming its rows here and tested as
`TestState<Name>Row<N>`; a new state or step is a row there and here.

A task with no record in the loop has no state: approved with its spec in the store, it waits for a dispatch (row 2).
Two are not states: a gate or a publish running (`submitted`, `moved`, `resolved` or `accepted`; `obor serve status`
shows the step `running`), and a watchdog's `stalled{idle}` (row 10, a fact: the task stays `working`).

## Timers

- **Delivery**: no delivery 5 min after the job prompt (its wake) → re-prompt
  once; no delivery 5 min after that → needs-you. The timers are folded from the facts, not recorded: a replay starts
  them afresh. An integrator job delivered, then idle with it: the stall timer's quiet time below (one nudge, then
  needs-you).
- **Blocked**: a `blocked` herdr status for 10 min since the agent was first seen blocked for the task → needs-you.
- **Stall** (Idle = 10 min): a state machine over observed quiet time. Its state per open task is `quietSince`
  (zero = no baseline) and `seenWrite`, the newest transcript write already accounted for, with the `stalled{idle}`
  and `needs-you{stalled}` facts in force. The first sample (and the first after a reset event) only sets
  `seenWrite`, to the transcript's write (none known: the sample's time), so an old transcript is never activity.
  A ready (idle or done) agent with an open task is sampled at every check. A sample is **active** (a child runs, or
  the transcript was written after `seenWrite`, even when the process check failed: a fresh write is evidence),
  **quiet** (no child, no newer transcript) or **unknown** (the process check failed, no newer transcript).
  **Reset events** take no sample and clear both: the status became working or blocked, the agent or its pane
  changed, the task changed, a replay.

  | Sample | Guard | Then |
  |---|---|---|
  | active | — | `seenWrite` = the write, `quietSince` = 0; stalled or escalated in force → fact `resumed` |
  | unknown, or a reset event | — | `quietSince` = 0 (unknown keeps `seenWrite`) |
  | quiet | no baseline | `quietSince` = now (no fact) |
  | quiet | not stalled, now − `quietSince` ≥ Idle | fact `stalled{idle}`, `quietSince` = now |
  | quiet | stalled, not escalated, now − `quietSince` ≥ Idle | fact `needs-you{stalled}` |
  | otherwise | | nothing |

  So the first quiet sample is a baseline, never also a verdict. Status age, the task's start and a pane's joining
  only reset the baseline, never count; a restart (replay) delays a stall by up to one period. A stall is followed
  by one nudge with the task (row 13); escalation counts from the stall.
- Notifications are at least once: a notification shown whose result fails to persist (or a crash before it) is
  shown again, after the retry backoff or on replay. Better twice than never.

## Transitions

"—" = no record or no effect. Class: see Crash classes. K = 2 sendbacks per task. Code cites rows by number, so
rows are not renumbered.

Every step's target is `branches.main`, never the branch the main checkout has checked out (gate, publish,
dispatch, merge evidence alike; specs are the store's, T-440). While the main checkout is on another branch or a detached HEAD the project's
pass pauses (`Loop.Checkout`): the loop's needs-you `loop: main checkout is on <b>, not <main>` (T-377's channel),
nothing submitted, gated, published or dispatched; it ends by itself with the first pass back on `branches.main`. A
publish already running refuses its fast-forward off the branch (an error: run again).

## Scheduler rules

Rule 1 is row 2a, rules 3 and 4 are rows 18–33; rule 2 (tier lists) and rule 5's cap and reserved slot are not built
(a dispatch is the lead's request, row 2; row 36).

1. **Readiness** (row 2a): a task with no loop record (its spec in the store) may be dispatched when every task it
   names as a dependency (`--after`) is merged.
2. **Dispatch by tier list**: not built.
3. **Accept / reject / sendback**: only the integrator gives them, only for the current candidate (patch hash). The
   gate's red is an automatic sendback, at most K = 2 per task, then needs-you. A gate conflict is a resolve job for
   the integrator, not a needs-you; needs-you only after that job fails or is rejected.
4. **Gate before accept; moved target**: nothing is accepted before its gate is green. Before publish and on a
   refused ff, re-gate; a byte-identical patch keeps the accept, a different one goes back to awaiting-accept.
5. **Integrator slot**: the integrator counts toward the project cap. While any task is submitted (its gate pending),
   green, awaiting-accept, conflict, resolving or resolved, dispatch leaves one slot for it. With no such task it may
   be stopped to free the slot (no cap yet: row 36).

## Concurrency (T-369)

One merge loop goroutine serves the project (a serve holds one, T-522), and only what needs serve's worktree is
serial: at most one of gate, publish and a `resolved` verdict's check holds the scratch at a time (a token). A gate or
a publish runs in its own goroutine holding that token; the task waits (no other step of it is decided) until the
effect's intent and result are folded, then the goroutine wakes the loop. Meanwhile the loop goes on with everything
else: dispatch steps, after-merge steps, prompts and verdicts. The event log stays the one
ordered writer (`Log.Do`, appends under its lock); the failure rule and the crash classes are unchanged: a gate cut by a
stop or a crash leaves its intent pending (not counted), and a replay runs it again under the same key. `obor serve
status` shows the step running (`running`); the loop's end waits for the running effects, which its context cuts.
Parallel gates are out (one scratch).

Drop vs a selected step (T-392, T-395, RV-42 #1): a step the loop selected starts only after one atomic check (under
the app's lock) that its task/attempt is still current and not ended (dropped, or a drop of it decided); the check
holds the task until the step returns (a gate or publish keeps the scratch and `running` through its effect). `obor
drop` never waits: in one section under the same lock it decides and marks the task ended, refused at once while a
step holds the task (`<step> is running; retry when it settles`) or a gate or publish is pending. The mark lands
before `dropped` is written (a failed write clears it and the drop fails), so no effect starts after `DROPPED`, and
none is still starting when it is returned. Submissions (`task_done`) check the mark under the
app's lock: none is decided once a drop is; one decided before it and recorded after changes nothing (a `submitted`
after `dropped` is ignored, `task_done` answers superseded; only a new dispatch reopens the task). A `dropped` fact
is terminal for the task whatever attempt it names (T-397, RV-42-verify-2 #1): a submission decided before the drop
may record the next attempt first, and `dropped` at the earlier attempt still ends the task, live and on replay; any
record of the task after it (submitted, a step result, a verdict) is ignored, a `dispatch` alone reopens it at its
attempt. So `DROPPED` is true once it is returned, whatever was decided before. No app-wide
request lock is held across a wait for external work. `obor drop` is wholly serve's (T-439): the mark holds while the
lane is given back (`LaneSetup.Free`, the worker stop), outside the verdict lock; a refused lane clears the mark.
