Plugins for agent kinds, terminal-neutral cores, and a project's own lane policy: obor's core runs the agents; what is specific to a CLI, a terminal or a language moves behind a plugin or into the config.

- **Agent kind plugins:** an executable that answers obor's kind protocol (`docs/agents/kind-protocol.md`) is an agent kind (`kinds.<name>.command`); obor caches its manifest at serve start and `obor init`. OpenCode is the first: it ships as its own binary, `obor-kind-opencode`, beside obor's.
- **Event feed and custom roles:** `obor events [--follow] [--after <seq>] [--json]` streams serve's records with a cursor, for integrations; a custom role can be given its own verbs.
- **Keep lanes:** a lane can run a list of tasks in one agent session, reusing its agent while the model and the config it started under are unchanged.
- **Priority:** a spec line `Priority: high` puts a waiting task first for the next free lane; `Ref: <id>` carries an external tracker's id into `obor status --json`.
- **A lane's env is the project's config:** `slots.lane_env` sets what a lane's processes see (`{cpus}` is the lane's budget); obor exports only generic facts (`OBOR_LANE_CPUS`, `OBOR_PROMOTION`). The flake parser and the retest command are config too (`merge.flake_regex`, `commands.retest`'s `{tests}`).
- **Agent start parameters give way to the project's files:** obor's policy flags yield to a project's committed CLI config (Claude Code, Codex, OpenCode).
- **Terminal-neutral core:** herdr's shapes stay inside the herdr adapter (`terminal.kind`); pane identity is obor's own `OBOR_PANE`; serve restores its panes when the terminal reconnects.
- **Restarts that tell the truth:** `obor restart` waits for the pane's shell after the stop, and reports a start as started only when the new agent is up, including while the terminal's listing still lags.
- **Codex 0.167:** obor's Codex start works again; a start checks macOS's quarantine first and names the Gatekeeper dialog when one blocks it.
- **Reviews from the event log:** what a review covered is serve's record, not a reading of git history; a lane's free state is one rule over serve's facts.
- **Faster, smaller test runs:** a plain `go test` runs unit tests only (no git); integration tests sit behind the `integration` build tag the gate passes; `-trimpath` everywhere keeps one Go build cache entry per package, and the nightly trims the cache.
- **Release from staging:** `make release` and `make ship` run from the main checkout on the loop's branch.

Upgrading: see `docs/UPGRADE-v0.31.md`. Go projects must add `slots.lane_env` (CPU budget and `-trimpath`) and `merge.flake_regex` / `commands.retest` (flake retests) to keep today's behaviour; every project caches the OpenCode manifest (`obor setup agents`) and commits `kinds.opencode.command`.
