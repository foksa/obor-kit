obor web gets a Setup page you can edit, and the owner can take a branch by hand with `obor drive`.

- **Setup page** (`obor web`, `#/<project>/setup`): difficulty levels and what each type runs (model, effort, max;
  unused types marked), lanes (pooled or typed), roles and the pause, and how dispatches spread by level and type over
  7 days or all time (dispatches from lanes since removed show their recorded type, else "unknown").
- **Edit the setup from the page**: difficulty order, lane types' model, effort and max, a lane's type, roles' types
  and the pause. Serve checks each change, writes `.obor/config.json`, commits it on main and tells the lead. The page
  accepts writes only from itself (Origin, Host and content type checked); a config file with uncommitted changes, or
  a key `.obor/local.json` overrides, is refused with its path. Edits run one at a time.
- **`obor drive <name>` / `obor drive <T-xx>` / `obor land <T-xx>`**: the owner iterates in a plain interactive agent
  on a task's branch (a new one, or one taken over from its worker), then lands it through the gate, review and merge.
  A red gate or a sendback goes back to the drive. `obor drive T-xx` again restarts a drive's agent that failed to
  start; a takeover stops the worker first and never races its submission.

Upgrading from v0.20: nothing required. After the v0.20 role move, `roles.reviewer.worktree` and
`roles.deep_dive.worktree` only reserve the name; delete them.
