## The fix-before items

### T-A: the guard checks one path and pi writes another (A F1, B2). Real, probed.

`toolEvent` resolves `input.path` with `path.resolve(cwd, …)` (`pi/obor.js:133`). pi's `write` and `edit` resolve it
with `resolveToCwd` (`core/tools/write.js:31`, `edit.js:92`, `path-utils.js:42`), which replaces Unicode spaces,
strips a leading `@`, expands `~`, and reads a `file://` URL, in that order (`utils/paths.js:100-122`).

Probe (the repo's `toolEvent` against the installed SDK's `resolveToCwd`, cwd `/Users/x/Work/obor-kit-wt/L-01`):

| `input.path` | the guard checks | pi writes |
|---|---|---|
| `src/a.go`, an absolute path | same | same |
| `~/.zshrc` | `…/L-01/~/.zshrc` | `$HOME/.zshrc` |
| `@/Users/x/Work/obor-kit/docs/design.md` | `…/L-01/@/Users/x/…/design.md` | `/Users/x/Work/obor-kit/docs/design.md` |
| `@src/a.go` | `…/L-01/@src/a.go` | `…/L-01/src/a.go` |
| `file:///Users/x/Work/obor-kit/docs/design.md` | `…/L-01/file:/Users/x/…` | `/Users/x/Work/obor-kit/docs/design.md` |
| `docs/a<NBSP>b.md` (also as an absolute path) | the name with the NBSP | the name with a plain space |
| `@~/x` | `…/L-01/@~/x` | `$HOME/x` |

For a worker the checked path is inside its own lane, so the guard allows it while pi writes the main checkout, another
lane or a protected file. A role with a write list fails closed instead (a false deny).

- **Likelihood in the owner's use:** low to moderate per task. A pi-sonnet worker mostly writes relative paths in its
  lane. `~/…` is common model habit, and `@path` is pi's own file syntax. No malice is needed.
- **Verdict: fix before.** It turns the guard's core denials into allows.
- **Fix:** `file()` applies pi's four steps in pi's order before `path.resolve` (about 10 lines, node built-ins only:
  `os.homedir()`, `fileURLToPath`). The Unicode class is `UNICODE_SPACES` in `utils/paths.js`.
- **Also in T-A (2 lines, recommended):** after an allow, write the checked path back into `event.input.path`. pi
  documents `event.input` as mutable (`docs/extensions.md:981-987`), and an absolute normalized path is a fixed point
  of pi's normalization. Then pi writes the file the guard looked at even if a later pi adds a normalization step.
  The live tier's guard row proves it does not break `edit`.
- **Tests:** one `toolEvent` row per form in `pi/obor.test.js`.
- B's wider fix for B2 (40-90 lines: the effective Bash command, tool provenance) is not needed for the tag; see
  "The decision's costs" below.

### T-B: every pi agent always reads as busy, so the stalled watchdog never fires (A F2). Real, probed.

- pi's MCP client starts each stdio server with `detached: true` (`pi-mcp/dist/transports/stdio.js:10, 82-88`).
- `obor mcp` is one of them on every start (`pi/obor.js:394`), and it lives as long as the session.
- `ChildOutsideGroup` answers busy for any descendant in another process group
  (`internal/background/background.go:237-253`). `Busy` is that answer (`internal/app/activity.go:186`).
- A busy sample is `active`, which drops the quiet baseline (`internal/app/watchdog.go:279-281`), so `stalled` and
  `needs-you{stalled}` are never recorded for a pi worker.

Probe: the SDK's own `StdioTransport` starting `sleep`: the child's pgid is its own pid (65947), not its parent's
(65923). With the code above that is conclusive; I did not start a real pi pane.

- **Likelihood:** certain, for every pi worker. It costs something only when a worker goes quiet without `task_done`
  after the Stop hook's one block.
- **Why it matters more than its own symptom:** the stalled watchdog is the net under several other points here:
  accepted RV-119 and RV-210, B6 (a first prompt pi refuses), B4 (a resume that exits) and B5 (a wake that starts
  nothing). With T-B merged those all end in a needs-you; without it they end in silence.
- **Verdict: fix before.**
- **Fix:** `ChildOutsideGroup` skips a process whose chain to the agent passes through a helper, by the rule `walk`
  already has (`background.go:269`): `oborMCP` anywhere, a direct child of the agent that is no shell, a direct child
  started with the agent. One predicate for both functions, not a second copy (AGENTS.md: one owner per helper).
- **Correction to A:** A says pi's real commands still count because "pi's bash tool runs every command through a
  shell". Not reliably: `bash -c 'sleep 3'` execs the command (probed: pi's direct child is then `sleep 3`, no
  shell), so a single long command would read as a helper. It does not matter for the stall timer: only Ready panes
  are sampled (`watchdog.go:126`), pi is `working` while a tool call runs, and pi has no background-job tool. But the
  task's table should not pin "a detached command under pi is busy" as a rule; pin the helper rows (a detached
  `obor mcp` and a detached non-shell direct child are not busy; a shell child with a child of its own is).
- **Claude is unchanged:** its helpers share its group, and its commands sit under a shell wrapper.
- **After the merge:** dispatch one pi-sonnet smoke task, let the worker sit idle, and check that `obor status` shows
  it quiet and the stall line comes after the idle time. No test covers a real pi process tree.

### T-C: a bare `pi "…"` from a shell tool runs pi headless and unguarded (A F3). Real, from source.

- pi picks print mode whenever stdin or stdout is no TTY (`main.js:79-89`). No agent's shell tool has a TTY.
- The guard denies only `-p`, `--print`, `--mode` and the config subcommands (`kinds/pi/kind/kind.go:146-148`,
  `internal/guard/shell.go:484-510`).
- The tests pin `pi -np "summarise"` and `pi -nc "x"` as allowed (`internal/guard/guard_test.go:278-280`). Both are
  headless runs from a tool.
- The nested pi loads no `pi/obor.js` (that comes only with `-e`), so its tools run with no obor guard while it
  inherits the caller's `OBOR_ROLE` and `OBOR_LANE`.

I did not run it: it would be a headless agent run. The mode choice in `main.js` is unambiguous.

- **Likelihood:** low in other projects (no reason to call pi). Moderate on this repo, where workers build and probe
  the pi kind, and for pi workers: pi has no subagent tool and its docs show `pi -p` for one, so a model denied `-p`
  tries the bare form next. pi is the only kind whose bare form runs headless; `claude`, `codex` and `opencode` fail
  without a TTY.
- **Verdict: fix before, first to slip** (see Answer).
- **Fix:** a manifest field that says the program is headless from a tool whatever its arguments, with the forms that
  run no agent listed (`--help`, `-h`, `--version`, `-v`, `--list-models`, `--export`, `list`). The guard denies the
  program unless a word before `--` is one of them. Flip the three allowed rows and add `pi "x"`,
  `pi --no-session -nc "x"` and `echo hi | pi`. `docs/agents/kind-protocol.md` gets the field.
- The session-start hook's "pi -p" text is the kind's deny wording; change it only if it names the flag.

### 5 and 6. The decision's costs (A F4, B2's rest, B3, A's design note). Accept; say them in the decision.

The 2026-11-28 decision keeps the user's pi extensions, packages and skills. These follow from it and are not stated
in its text:

- obor's `tool_call` handler runs first, because CLI `-e` extensions load before the user's
  (`core/resource-loader.js:426, 803-815`). A later handler may change `event.input` after the allow, with no
  re-check (`docs/extensions.md:981-987`). An extension may also replace a built-in tool by name.
- A `shellCommandPrefix` setting is put in front of the command after the guard read it
  (`core/tools/bash.js:185-198`).
- A server in `~/.pi/agent/mcp.json` or the project's `.pi/mcp.json` wins over an extension's registration of the
  same name (`extensions/mcp/index.js:245-260`, `docs/mcp.md:264`), and the guard approves by name
  (`internal/guard/guard.go:552-581`).
- Extension code that calls `pi.exec` or Node itself never reaches the guard.
- Every tool a user extension registers is denied for obor's agents as `unguarded` (fail closed).

The owner's pi today: `settings.json` holds three keys (version, provider, model), there is no `extensions` directory
and no `mcp.json`. So none of this can happen now.

B3's other half is not a bypass: the extension registers the lane checkout's `.agents/mcp_config.json`
(`pi/obor.js:354, 395`) and the guard approves the main checkout's keys. A difference means a denied call or a missing
tool, never an allowed one.

Recommendation: the lead proposes one sentence for the decision ("the guard checks a call as obor's handler sees it;
the user's extensions, shell prefix and `mcp.json` act after it or beside it"). If the owner starts using pi
extensions or pi MCP files, take the collision warning (the extension reads both `mcp.json` files at load and warns
on a name it registers, 20-40 lines) and probe `Object.freeze(event.input)` (5 lines; `edit`'s `execute` must not
write its own args).

### 9. A resume with `--session <id>` can exit or ask (A F7, B4). After.

Real, from source:
- An id with no file exits with "No session found matching" (`main.js:363-365`). pi writes a session file only once
  a user or assistant message exists (`core/session-manager.js:799-827`), and launch does not check a pi transcript
  (`internal/launch/launch.go:1001-1006`: pi's sessions are not obor-named).
- An id found only under another cwd asks "Fork this session into current directory?" (`main.js:354-360`).

A worker's restart resumes in its own lane a session that took its job wake, so both cases need something else to
have gone wrong first (a refused first prompt, a moved directory). They become ordinary for a pi role that starts
idle and is restarted before its first brief. No pi role exists yet.

- A's one-line fix (`--session-id <id>`, `main.js:383-390`) is the right shape. B's 60-110 line preflight is not
  needed.
- It is not a free rider: it changes how pi is launched, so it needs the live tier (AGENTS.md), and a session
  created under the old id reports `source: resume` (`pi/obor.js:477`). Its own task, before the first pi role.

### 10. The extension and Go find the project differently (B1). After, both extensions in one task.

Real, but narrower than "High":
- The extension looks for `.obor/config.json` at or above the cwd (`pi/obor.js:94-99, 354-355`). Go reads the main
  checkout through the git common dir (`internal/project/project.go:48-68`).
- They differ only when the lane's tree lacks the config, which means it was never committed. `obor init` in a repo
  with commits leaves it for the owner to commit (`internal/setup/init.go:227-275`). A lane cannot "predate" it
  otherwise: lanes branch from the target.
- OpenCode's plugin has the same lookup (`opencode/obor.js:138-141, 616`). This is not new with pi.
- It is seen: `obor status` warns `no-plugin` on a working lane whose plugin kind left no marker two minutes after
  its start (`internal/view/view.go:525-547`; pi's hooks are `plugin`).

Fix after: when the start is obor's (the identity variables are set), the extension does not gate on the tree and
lets the Go hook decide (it stands down outside a project). About 10 lines per extension plus a sibling-worktree row.
B's 35-75 lines (carry a root through the launch) stores a name obor can derive.
