# OSC 7501 (Program Status Protocol) for obor

Question (owner 11-23: "rex should implement this and probably herdr core also"): what the spec says today, what hc
implements, what Rex and herdr do with it, which agent CLIs emit it, what obor gains or drops per terminal.

- Date: 2026-11-23. macOS (Darwin 27.2), one machine.
- Installed here: hc 0.1.21, herdr 0.9.5, Rex Beta 0.1.0 (the app bundle; no `rex` CLI on `PATH`), Claude Code
  2.1.330, Codex 0.170.0, OpenCode 2.2.0, agy 1.5.15 (`<cli> --version`).
- Not done: no hc, herdr or Rex terminal was driven (the guard denies it; `AGENTS.md` bans the default session). The
  CLI probes below ran each CLI interactively in a scratch pty (a Python `pty.fork` harness in the session scratchpad,
  cwd an empty scratch dir, killed after 12 s, no prompt sent, no turn run). Spec, blog, PR and issue facts come from
  fetched pages (a fetch agent read them; quotes are short); the ones I did not read myself are marked.

## Answer first

1. **Spec / hc.** The spec is at revision 0.4 (2026-10-10). hc 0.1.21 relays root-record status (`state`, `kind`,
   `msg`, `app`) and obor reads exactly those four fields (`internal/hc/panes.go:32-38`). It does not read `id`,
   `title`, `progress`; it folds `error` into `idle` (`internal/hc/panes.go:100-108`). hc's own revision number and
   its nested behaviour are not documented in anything I could read; the spec itself says nothing about multiplexers.
2. **Rex** is the spec's reference consumer and the author's own project: session picker, tab headers, a Lua event.
   Its binary (0.1.0) has `program_status`, `program_status_changed`, `program_status_removed` and answers the query.
   An adapter reads the `program_status` field and that event; the payload shape is unprobed (plan R3).
3. **herdr 0.9.5 (the TUI obor drives today) does not consume 7501**, does not answer the query, and the upstream
   request for it was closed "not planned"; a draft PR (#5172) is open. herdr-app and herdr-core take status from
   7501 only.
4. **All four installed kinds emit it natively**: Claude 2.1.330, OpenCode 2.2.0, agy 1.5.15 and Codex 0.170.0
   (probed here). Gating differs: Claude and agy send nothing unless the terminal answers the query, so under
   herdr 0.9.5 Claude emits nothing. No kind emitter is needed for the five status words; one would be a second
   status path with a real overwrite hazard (below).
5. **Recommended order:** keep hc as is and fix its three small gaps; Rex adapter after probe R3, reading 7501 the
   same way; ask herdr upstream to answer the query and merge #5172; no hook- or plugin-written 7501.

## 1. The spec as of today, and hc

Source: https://www.superlogical.com/rex/docs/build/program-status ("Program Status Protocol (OSC 7501)", read in full
by the fetch agent).

| Part | Spec |
|---|---|
| Revision | 0.4, 2026-10-10. History: 0.1 (09-28), 0.2 (10-06), 0.3 (10-07), 0.4 (10-10). 0.4: the feature reply may list `states` and `kinds`; terminfo removed. 0.3: absent `progress` = indeterminate; programs may send without detecting |
| Grammar | `OSC 7501 ; pairs ST`; `pairs := pair (":" pair)*`; `key := [a-z]+`; `value := [A-Za-z0-9_.,+/=-]*`. ST is `ESC \` or BEL. `msg`, `title`: base64 UTF-8, no control characters once decoded. Malformed pair skipped; unknown key ignored; repeated key last wins |
| Keys | `state` (required: idle, working, done, blocked, error, clear; unknown or missing → whole report ignored), `id`, `kind` (permission, question, auth; only with blocked), `progress` 0-100 (working or blocked), `app` (`[A-Za-z0-9_.+-]{1,32}`, inherited from the nearest ancestor), `title`, `msg` |
| Records | one per `id`; no `id` = root. A report replaces its record whole (keys not re-sent are gone, so `app` is sent every time). Id: `/`-separated segments, 8 levels, 128 bytes. `/` means parent/child for clear and `app` inheritance only. Records belong to the terminal, not the screen; RIS removes all, DECSTR none |
| Lifetime | no heartbeat. Process exit or the next shell prompt (OSC 133 `A`) MUST drop working and blocked, MAY drop idle; done and error survive both |
| Clear | `state=clear` removes the addressed record and everything beneath it; with no `id` it removes every record of the terminal |
| Query | program sends `OSC 7501 ; ? ST`; a supporting terminal MUST reply `OSC 7501 ; ? [: states=…] [: kinds=…] ST` (missing lists mean the original five states and three kinds). Terminals MUST ignore unknown OSCs, so a program may send unqueried. Timeout: send DA1 (`CSI c`) right after; if DA1 is answered first, unsupported |
| Limits | sequence 4096 bytes; key 16; `msg` 2732 encoded / 2048 decoded; `title` 256 / 192; 256 records per terminal (terminal MUST hold 64; least recently updated goes first); a report that breaks a limit is discarded whole |
| Security | everything is untrusted; refuse control characters; no markup; the only bytes written back are the query reply; anything shown SHOULD name its terminal; rate-limit external effects (notifications) |
| Multiplexers, nesting | **not specified.** The page defines "terminal" as one window, tab, split or pane on one PTY and says nothing about tmux passthrough or nested multiplexers |

Related facts from other pages:

- Ghostty PR #14560 (merged 2026-10-06, merge commit `a4aacd9`): libghostty-vt parses it and answers the query; the
  terminal keeps no records (the embedder does); the Ghostty app ignores the reports ("for now"). kitty implemented
  0.4 on 2026-10-13: working, blocked and idle drop at a new prompt, done and error when the window gets focus.
- OpenTUI #1657 (merged, emitter for OpenCode): "Reports are never wrapped in tmux or GNU Screen passthrough," because
  the outer terminal "cannot tell panes apart or see the program exit." (Quoted from the PR page's downstream list.)
- A third-party guide says tmux drops the sequence unless wrapped (https://stackness.dev/blog/osc-7501-program-status-terminal-protocol-for-coding-agents; search snippet, not read).

### What hc implements (hc 0.1.21)

- **Source:** "Status comes from the program's OSC 7501 reports: `idle`, `working`, `done`, `blocked`, `error`; plain
  programs report none. Do not guess status from screen text." (`hc --skill`, "Status, recovery, and cleanup").
  herdr.dev/core says the same: "No screen scraping, no list of known agents."
- **Clear:** `hc --skill`: "On Unix, status clears when the root interactive shell returns to the foreground.
  Direct programs and shell command/script wrappers keep status while their tools run. Returning to a nested shell is
  not detected; a shell's own status and a backgrounded agent's status clear." Earlier, on 11-05, the herdr-core
  maintainer closed a PR doing core-side clearing: "we've decided not to clear statuses from the core side … an agent
  that exits should send state=clear (or done/error) on the way out" (herdrdev/herdr-core#73, fetched). The two
  statements disagree on date or scope; which holds at 0.1.21 beyond the skill text is not verified.
- **Query:** a comment in the herdr-core thread says hc answers it (`docs/plan/herdr-core.md:71`, quoting the 11-04
  comment). Not re-verified here: reading hc's reply needs a terminal driven in hc.
- **Records:** hc's terminal record carries `status` and a `records` map (P1: OpenCode "fills `records` keyed by its
  session id", `docs/research/hc-probes.md:227`). obor's `Record` has no such field
  (`internal/hc/panes.go:17-30`): nested ids are not read.
- **Nesting / pass-through:** nothing found. Each hc terminal is one pty, so a program that is a terminal's own
  foreground reports directly; one inside tmux inside hc depends on tmux. In my pty probe Claude 2.1.330 with
  `TMUX` and `TERM_PROGRAM=tmux` set emitted the same bare sequence (no `ESC P tmux;` wrapper), as did agy and OpenCode
  (all three probes: wrapper absent). So a nested agent's reports reach hc only if tmux passes them: unverified, no
  tmux was run.
- **Observed at hc 0.1.21 (`docs/research/hc-probes.md` P1):** Claude: idle, working, done (then done with `msg`),
  blocked/permission ("trust this folder", "approve Bash: …"), clear on `esc`; Codex 0.169/0.171: same words, `blocked`
  with no `msg`, its trust and update dialogs report nothing; OpenCode 2.2.0: never `done`, an API error shows as
  `idle`, `blocked` with title.
- **obor's read:** `statusWord` maps idle/working/blocked/done as they are, `error` → `idle`, anything else
  `unknown` (`internal/hc/panes.go:100-108`); the kind from `status.app` through `Caps.App`
  (`internal/hc/panes.go:73-88`, `internal/agents/agents.go:499`). `Caps.App` is set only by Claude
  (`internal/agents/claude/claude.go:712`, `claude-code`) and by a plugin manifest. agy reports `app=antigravity`
  (probe below) and falls back to the `obor.kind` label (`panes.go:70`).

**Gaps (spec vs obor's read of hc):** `progress`, `title`, `id` records not read; `error` loses its word (the plan
chose that: its `msg` is logged); `kind` read but only shown. hc's own revision (0.4 or earlier) and size limits: not
stated anywhere I could read.

## 2. Rex

- **Consumes it, as the post and spec say.** The spec's own "Rex shows this in its session picker and tab headers,
  and Lua can react to `terminal.program_status_changed`"; planned: mobile push, a unified inbox. The post (Mitchell
  Hashimoto, 2026-10-06) says he implemented it twice, in libghostty and "in parallel" in Rex (fetched; the post says
  nothing more about how).
- **In the installed binary** (`/Applications/Rex Beta.app/Contents/MacOS/Rex`, 0.1.0, `strings`): `program_status`,
  `program_status_changed`, `program_status_removed`, "invalid OSC 7501 report", "OSC 7501 sequence too long", and the
  reply `]7501;?:states=idle,working,done,blocked,error:kinds=permission,question,auth`. So it answers the query with
  the full lists.
- **What an adapter reads** (`docs/plan/terminal-adapters.md` step 9, R3 at line 157): the block's `program_status`
  (state, kind, msg, app; probably the id records too) and the stream's `terminal.program_status_changed` /
  `_removed` events (`docs/research/terminal-port-advice.md:83`). The wire shape of the payload is **unknown** until
  probe R3; every field name above except the three event/key names is from the spec, not from Rex's API.
- Rex has no agent layer, so on Rex 7501 is the only status; blocked comes from `kind`, and a send's guard is obor's
  (`terminal-port-advice.md:75`, need 4).

## 3. herdr (default terminal, today)

- **herdr 0.9.5 (the TUI) does not consume 7501.** `strings` on the binary finds no "7501"/"program status" text;
  a user in anthropics/claude-code#106772 (2026-11-15) says "its binary contains no OSC 7501 handling at all"; its
  status is screen detection plus integrations (0.9.5 notes: "Codex status comes from screen detection again",
  `~/.config/herdr/release-notes.json`).
- **Upstream state (fetched):** herdrdev/herdr#5069 "Support the Program Status Protocol (OSC 7501) as a generic agent
  state source" opened and closed 2026-10-08, "Closing under the bugs-only issue policy", moved to Ideas.
  herdrdev/herdr#5172 "feat: add OSC7501 agent reporting" (JJLiebig, spec 0.4, libghostty parser backported): open
  **draft**, no maintainer reply, no release; users ask for it for the TUI (2026-11-12, 11-17). The maintainer's
  position (herdr-core#73, 11-05): herdr "doesn't detect agents itself, it just shows what they report through the
  open osc 7501 protocol" (said of herdr-core and the app).
- **Effect on obor today:** Claude Code 2.1.330 sends the query then DA1 and emits nothing unless the 7501 reply
  comes first (probe below; a user reports the same for 2.1.326 under herdr 0.9.5 on #5172, 2026-11-17). So on
  herdr the screen stays the only source for Claude.
- **What to ask upstream:** (1) answer `OSC 7501 ; ?` (the minimal fix: Claude and agy then start reporting, even if the
  TUI ignores the records); (2) merge #5172 or equivalent into the TUI; (3) expose the records in the API
  (#5172 adds `pane.get`/`pane.list` `program_status`); (4) state the clear rule (agent job exits under a shell:
  who clears).

### Could obor's kind emit it for a CLI that does not?

Every installed kind already emits, so the question is only about gaps: Codex's trust and update dialogs (silent,
`docs/research/hc-probes.md` P1), OpenCode's missing `done` and API error as `idle`, and Claude/agy under a terminal
that does not answer the query. Mechanics:

- **A hook or plugin writing to the pane's tty.** From a Claude tool subprocess `/dev/tty` fails here
  (`device not configured`; `ps` shows that process with TTY `??` while its parent `claude` has `ttys034`; same fact as
  P9's "tpgid 0"). A hook would have to find the agent's tty from its ancestors and open that device by name: possible
  in principle, **not tried** (it would have written into a live pane). Plan R3's second half asks exactly this
  (`docs/plan/terminal-adapters.md:157`).
- **The second status path risk.** A report replaces its record whole and the last one wins, so an obor-written root
  record races the agent's own: a hook's `working` after the agent's `done` leaves the pane `working`; a stale
  `blocked` outlives the prompt. Using a separate `id` keeps the records apart, but consumers show the root
  (hc's `status` is the root; obor reads only it), so the obor record would be invisible to them. A kind that writes
  needs its own clear and exit rules, which is the status path obor dropped on hc ("Step 5 is dropped",
  `docs/plan/herdr-core.md:33`; HD3/HD4 at `docs/decisions.md:33`).
- **Where a hook already exists** (Claude's permission hook; agy's `.agents/hooks.json`) obor has the event itself and
  needs no terminal to learn it (D3a, `docs/plan/terminal-adapters.md:22`: "hooks, then 7501; never the screen").

## 5. What obor gains or drops, per terminal

| | herdr TUI 0.9.5 (default) | hc 0.1.21 | Rex 0.1.0 |
|---|---|---|---|
| Status source today | screen detection + herdr integrations | the agents' 7501 (relayed) | 7501 (relayed), per the spec page and binary |
| Idle / working / done | screen heuristics; Codex by screen | from the program; Claude, Codex `done` after a turn, OpenCode ends at `idle` | same words, Rex API shape unprobed |
| blocked / needs-you | screen; Claude has a hook | `blocked` with `kind` and `msg`, Claude/Codex/OpenCode at permission prompts; Codex trust/update dialogs silent | `blocked` + `kind`; guard is obor's |
| Gain from 7501 | answering the query alone makes Claude and agy report; then `kind`/`msg` replace screen text | already taken; more available: `error` word, `msg` for the web card, `progress`, `title`, records | adapter reads the same fields at no new cost |
| Drop | screen rules for Claude (only after herdr consumes 7501 and with the hook still the blocked source) | nothing further | n/a (no screen path exists) |
| Web card / needs-you line | could show `kind` + `msg` only if herdr exposes the record (#5172 adds `program_status`) | `status.kind`, `status.msg` are available now (`internal/hc/panes.go:32-38`) | `msg`, `kind` from the event |

Notes on the table: the web card and needs-you text are not read from 7501 in obor today (obor reads `State` and
`App`, and logs `error`'s `msg`); using `msg` is untrusted text (the spec: refuse control characters, no markup; show
which terminal it came from).

## Recommended order

1. **hc: no new path; fix the small gaps** (a task for the lead to decide): keep `error` as its own word or log its
   `msg` as now; read `records` only if a card wants a worker's sub-status; check hc's reply to the query at the
   version obor requires (no live probe of it was possible here). Codex's dialogs: stay with the start's screen read
   (the plan's choice).
2. **Rex: run probe R3** (reading `program_status` and the event for Claude, Codex, OpenCode, agy) before step 9;
   then the adapter passes the status on like hc's. Cost is small once the payload shape is known.
3. **herdr: ask upstream**, in the order of §3 (answer the query first). Until then keep screen detection and the
   Claude hook; do not rely on 7501 on herdr.
4. **No kind-written 7501.** Revisit only if probing shows a CLI that is silent where obor needs a word and has no hook,
   and then only with the second-path rules (one writer, an owned `id`, a clear on exit) written first.
