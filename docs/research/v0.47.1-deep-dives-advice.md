**B's "hold the tag, 3 blockers" is overstated.** All three are real observations, none is a blocker by likelihood or
damage:

- **F2.1 is a real bug**, and B's proposed fix is not enough (probe below). It needs the target to stop tracking a
  path that is in the lane's link set, while a sent-back task's branch still tracks it, and then a failed merge
  commit or a cut between the merge and the commit. obor-kit has no `lanes.links`. When it does hit, the lane's

## B's three blockers, settled by probe

### F2.1: the link put back during an open merge blocks `git merge --abort`. Real.

`Lane.Sync` runs only `git merge --no-commit` inside `project.WithLinks` (`internal/checks/lane.go:157-164`), so
`WithLinks` reconciles the links while the merge is still open (`internal/project/worktree.go:140`), and the commit
comes after (`lane.go:178`). When the merge removed a tracked file whose path is in the link set, the reconcile puts a
symlink there. If the commit then fails, `git merge --abort` must restore the tracked file and refuses.

Probe (real git, fixture: `lanes.links: ["conf/local.env"]`, main commits `conf/local.env`, the lane branches from
there, main then runs `git rm --cached conf/local.env` and commits; the commit fails through the test's
`commitFailShim`):

- Run 1: `commit the merge …: the commit failed; git merge --abort …: exit status 128: fatal: Could not reset index
  file to revision 'HEAD'.` The lane keeps `MERGE_HEAD`, status `D  conf/local.env` + `?? conf/local.env` (the link).
- Runs 2 and 3 on plain git: the same exit 128 at the replay's abort (`lane.go:117`). It never recovers by itself.
- With a commit that succeeds the end state is correct (merged, the path is obor's link, the lane clean).

**B's fix (move the commit inside the `WithLinks` closure) fixes the failed-commit case only.** I applied it as an
overlay: a failed commit then aborts cleanly and the replay merges. But when the abort fails too (serve's own stop
cuts the step, so the commit and the abort both die with the context), `WithLinks`' failure path still reconciles with
the merge open (`worktree.go:137`), and the replay is stuck exactly as before (probed).

**The fix that converges in every case (probed, both parts together):**

1. The replay's abort takes obor's links out of its way first. An abort is a checkout of `HEAD`, so it gets the same
   link handling as any checkout:

   ```go
   if _, open, err := git.Verify(in.Dir, "MERGE_HEAD"); err != nil {
       return port.Synced{}, fmt.Errorf("read MERGE_HEAD of %s: %w", in.Dir, err)
   } else if open {
       err := project.WithLinks(l.Cfg, in.Dir, "HEAD", l.linkGit(ctx), l.say,
           func() error { return l.abortMerge(git, in.Dir) })
       if err != nil { return port.Synced{}, err }
   }
   ```

   This replaces the plain `abortMerge` at `lane.go:117`; the reconcile at `lane.go:120` stays. Only a lane with an
   open merge pays the extra `git status`.
2. The commit moves inside the `WithLinks` closure (merge, then commit, a failed commit aborted there), so the
   reconcile sees the merge commit as `HEAD` or the lane as it was. The separate abort and reconcile at
   `lane.go:179-184` go.

With both: a failed commit leaves the lane as it was and the next run merges; a hand-made "merge open plus link"
state and the commit-and-abort-cut state both replay to `merged`. Part 1 alone also unjams every replay, but the
first run still ends with the merge open. `TestLaneSync*` and the package's unit tests pass on the patched file.

Expected test change (T-A): two new real-git subtests in `TestLaneSyncKeepsTheLinks` (a git behaviour no test
covers): "the target stops tracking a linked path and the commit fails: aborted, the tracked file back, no
`MERGE_HEAD`; the next sync merges and the path is the link" and "a cut left the merge open with the link at a path
HEAD tracks: the replay aborts and merges". The worker checks `internal/checks`' `git_procs` budget.

### F2.2: `task_done` during `lane.sync`. Accepted, yes; a race, no.

`fetch.go:367-370` clears `busy` for every task that is not being dropped, because the only step that used to hold a
working task was the fix job's send. Rig probe (`Sync` blocked on a channel, the worker's `task_done` under a new call
id sent meanwhile):

- reply `submitted`; the only record written while the sync is blocked is `2 fact submitted`;
- after the sync returns: `2 result lane.sync`, then `2 intent submit`, `2 result submit`, gate, test (red again),
  `2 fact sendback`, attempt 3's `lane.sync` and fix job.

So `Scratch.Submit` never runs beside the merge (`drive` runs a task's steps one after another, `loop.go:664-670`;
`submit` runs its effect inline, `steps.go:179-199`). What is lost: the attempt is submitted without its fix job ever
going out, the same work goes through the gate again and one of the two sendbacks is spent. The same was possible
before T-1573 in the instant between the sendback and the fix job; `lane.sync` makes that window as long as the merge.

### F2.3: a pending `lane.sync` after a restart does not make its task busy. Real, narrow.

Fold probe (the sent-back log plus attempt 2's `lane.sync` intent, as a restart reads it): `busy=""`, the task may be
moved and submitted. A move's redo dispatch then leaves attempt 2's intent open for good (`state dispatched attempt
3, lane.sync still open true`), and so does a `submitted` fact (`state submitted`, step `submit`). Neither path aborts
a merge the cut left open: `Lane.Prepare` with `Redo` skips the checkout (`lane.go:83`) and `Scratch.Submit` runs
`git add -A` and a commit (`scratch.go:79-85`), which concludes the open merge. Damage needs the cut to fall inside
the merge itself, and a move or an unprompted `task_done` before the first pass. The window is long only while serve
is not connected to the terminal (no pass runs).

**One fix for F2.2 and F2.3 (probed as an overlay):**

- `states.go:195`: `{step: event.StepSync, busy: func(mtask) int { return 0 }}`. A pending intent then reads
  `T-1 has lane.sync pending`; a needs-you still frees the task (`states.go:319`).
- `fetch.go:368`: `if !p.ended[c.Task] && !mt.syncDue() {`. The comment's reason ("the step holding it is the one that
  sent this job") is not true of `lane.sync`, which sends no job.

With both, the probe's `task_done` is refused (`task_done T-1: T-1 has lane.sync running; retry when it settles`),
nothing is recorded and the fix job goes out. The package's tests pass except
`TestStepTableGivesTheReadersTodaysAnswers` (`states_test.go:607`), which pins `lane.sync: busy ""`: that row's
expectation changes. New: one rig row in `lanesync_ext_test.go` for the refusal. The other readers of `busy` get the
right answer for free (the worker-start rule `workerstart.go:53`, the keep lane `keeplane.go:279`, move, resume, the
lead's sendback, land).
