# Advice: the two v0.44 deep dives (Opus, agy)

Asked by the lead, 2026-11-22. Inputs: `docs/reviews/DD-v0.44-opus.md`, `docs/reviews/DD-v0.44-agy.md`, the claims
(`docs/releases/v0.44.0.md`, `docs/UPGRADE-v0.44.md`), `docs/accepted.md`, the 11-22 entries of `docs/decisions.md`.
Every finding was read against the code at HEAD `449a3038`. One live probe was run (B1). The agy binary's strings were
searched for the tool names agy's review cites. Nothing else was run: no agy or OpenCode session, no conformance tier.

## Answer first

**Do not tag yet. Two small tasks and four text edits come first; everything else is a v0.44.1 wave or
extraction prep.** Neither deep dive found a bug on obor-kit's own Claude/Codex path.

Before the tag:

1. **agy `deliver` runs whatever program the inbox record names** (Opus #1, agy missed it). An agy agent can set that
   record from its environment or its worktree, and serve then runs the program outside agy's sandbox and outside
   obor's guard. The agy lead runs plain auto mode by today's decision, so the sandbox is its boundary. ~20 lines.
2. **The OpenCode plugin allows a tool call when the guard exits with anything but 0 or 2** (agy B6, Opus missed it),
   against the "Hook transport" contract this release publishes. 2 lines.
3. **A resumed OpenCode lead has no inbox until its first turn** (agy B5, Opus missed it), so "an idle OpenCode lead
   is woken by a line" is false after a plain `obor restart <lead>`. ~15 lines in the same file as 2.
4. **Text:** `UPGRADE-v0.44.md` says obor's hooks guard every agy agent; they check three tools. Say which, and say
   that an override's lists replace the user's.

The compared verdicts: Opus says ship, agy says hold for six high-impact bugs. Of agy's six, two are must-fix (B5,
B6), two are real and belong in the next wave (B7, B9), and two are overstated (B4, B8). Opus's top finding is the
one agy missed.

The decisions, short (details in "Open decisions"):

- **Unguarded agy tools under `always-proceed`:** real gap, size unknown. Probe first, then fail closed on tools the
  transport does not know. Until then the upgrade guide says so.
- **Separate binaries or one obor:** link the kit's kinds into obor, answering the protocol in process. I recommend
  revisiting the "into plugin binaries" half of D5. Most of the extraction's obstacles in both deep dives exist only
  because a kit kind is a separate process.
- **agy's accepted.md sweep:** delete the three RV-220 lines and one duplicate RV-139 line, take RV-215 (now ~10
  lines), keep the rest.
- **The extraction needs first:** the binary decision, then no kind call under `App.mu`, then one protocol-prep task.

## 2. The two reviewers

Opus was narrower and accurate. All 14 of its findings checked here hold, its likelihoods are calibrated, its probes

(B5, B6) and scoped its accepted.md sweep to the lines v0.44 touched, so it left three dead lines in. agy was

## 4. Open decisions

### agy's unguarded tools under `always-proceed` (agy F1, Opus D4c)

Two 11-22 decisions meet here: obor-kit's agy workers run `always-proceed` because obor's guard is the boundary, and
agy agents keep the user's own plugins and MCP servers "until a switch is found". The guard is registered for three
tools (`hook.go:57`), and an unknown tool is passed to agy's own check (`:123-126`), which under `always-proceed`
approves it. A Claude lane does not have this gap: it starts with obor's MCP server alone.

Recommendation:

1. Now (A3): say it in the upgrade guide.
2. Probe P1. The transport's design depends on its answers, and a guess here either leaves the hole or breaks agy
   lanes.
3. Then W10: if a matcher can catch every tool, the transport denies by name any tool it does not map, in an obor
   project. That is the project's own rule ("an empty derived value is an error, never a default") applied to tools,
   and an agy self-update that adds a tool then shows as a named deny, not as a silent bypass.
4. For other servers' MCP tools the hook is the switch D2 was waiting for: `call_mcp_tool` carries `ServerName`
   (`agy-probes.md:157`) and its matcher fires. Map it to an event the guard reads and let the guard deny a
   lane-bound role any server but obor's. The rule belongs in the guard, not the transport.

**Revisit:** D2's "keep loading the user's plugins until a switch is found", once P1 is in.

### Kit kinds as separate binaries or one obor (agy E8)

agy's size argument is wrong (3 MB per kind binary). The better arguments are in both reviews' extraction sections,
and they share one cause: a kit kind is a separate process with a cached manifest.

| Obstacle | Separate binaries | Linked into obor |
|---|---|---|
| A process per transcript chunk, per lead prompt (Opus E1, agy E4) | needs a protocol change (`turn` by path) | a function call |
| The guard needs a manifest cache before the first session (Opus E3, agy E2) | needs a static manifest file or a describe in a hook | no cache: `plugin.Ensure` already skips a kind answered in process (`plugin.go:219-221`) |
| Every start behind every kind's fetch (Opus E5) | grows with each kind | one binary |
| `obor kind` exec, `OBOR_EXE` (B1), the shim's `kind` path (W1) | stay | the exec goes; the shim still must not fetch |
| Rig tests need an in-process handler per kind (Opus E6) | a test-only twin | the production path |
| obor and a kind binary of different versions | possible after a partial fetch | not possible |

Recommendation: the kit's kinds are Go packages in this repository, so link them into obor and register each as the
in-process handler tests already use (`plugin.Local`). The protocol stays the only interface to a kind, which is
what the extraction is for: the compiled-kind interfaces of `agent-kinds-advice.md` §3.3 are deleted either way. A
config's `agents.kinds.<name>.plugin` line keeps running an external command over the same protocol.

What this costs:

- The process path loses its production users. Keep one static conformance row that runs a kit kind as a built
  binary, so the path a third-party kind uses does not rot.
- A kind's panic becomes its caller's. The handler recovers, as `guard.Run` does.
- It reverses half of D5 ("into plugin binaries") and the `obor-kind-opencode` and `obor-kind-agy` release assets.
  The upgrade is one release where the shim stops requiring them.

"Multi-call obor" in the narrower sense (one binary, still a process per call) fixes only the fetch and version rows.
I do not recommend it as the end state.

**Revisit:** D5's form, before the Codex task is specified. Its order (codex, then claude, after agy has run in lanes
for a few days) stands.
